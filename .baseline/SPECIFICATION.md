# Shared site template: specification (1.7)

Status: 1.7, carrying the owner's decisions of 2026-11-03 through grclibrary.ai's change request (search results mode and facets, the matrix with presets, the left-rail page), the sticky table correction (the sticky scroll box), the hidden-content correction, the decisions after 1.5.1 (dark mode near black with the site's own tint, the light and dark switch, site-owned palette colours), the documentation corrections reported by auditthis.ai after adopting 1.6.0, and the owner's decisions of 2026-11-04 (the About line that wraps at 320 px, and the large matrix table capabilities requested for crosswalk pages), published with baseline package 1.7.0 at https://posluns.ca/baseline/1.7.0/SPECIFICATION.md (1.0 was approved on 2026-11-02 and published with 1.0.0). A correction is a new version with a changelog entry. The owner chose the Atrium direction and approved its design through review round 11; this document describes the Atrium as built in the mockups (`site/drafts/atrium/` on the `mockups` branch of jposluns/posluns_site, `build.py` and `template.css`) and is the normative document the 5 project repositories implement from. The content guidelines 1.4 (`CONTENT-GUIDELINES.md` in the same package) govern the wording; the Clean Language standard (https://cleanlanguage.ai) governs the prose.

Every value in this document is taken from `template.css` or `build.py`. Where a value is rounded or inferred, the text says so.

## 1. Purpose and scope

One template for 6 project sites, so that each looks and behaves as part of one family and differs only in its colours, logo, illustration and content:

| Order | Site | Hue | Repository that holds the site |
|---|---|---|---|
| 1 | secureconfig.ai | red | jposluns/secureconfig (`site/`) |
| 2 | opfiles.ai | orange | jposluns/guardrails (`opf/site/`) |
| 3 | auditthis.ai | yellow | jposluns/auditthis.ai (`site/`) |
| 4 | cleanlanguage.ai | green | jposluns/cleanlanguage (`site/`) |
| 5 | aiqt.ai | blue | jposluns/guardrails (`site/`) |
| 6 | grclibrary.ai | purple | jposluns/grc_library (`.web/`, built at deploy) |

posluns.ca keeps its current design and hosts the template package. vendorreplies.ai is out of scope for this version.

Headers for `/baseline/*` on posluns.ca: `Cache-Control: public, max-age=31536000, immutable` and `X-Robots-Tag: noindex`. Sites copy the files at build time and never fetch them at runtime, so no CORS header is required.

## 4. Adoption in each repository

1. Obtain the version as its archive, `https://posluns.ca/baseline/baseline-<version>.tar.gz`, and verify the archive's digest against `https://posluns.ca/baseline/SHA256SUMS` before unpacking. Never verify file by file over the live domain: Cloudflare injects scripts into HTML served there, so an HTML file fetched from the site is not the published file.
2. Copy only the runtime and licence files into the site's own asset folder (proposed `assets/baseline/`): `baseline.css`, `palettes.css`, `fonts.css` and `fonts/` with the 4 licence files, `copy.js`, `select.js`, `search.js`, `rail.js`, `matrix.js`, `scheme.js`, `logos/`, `marks/` with `marks/NOTICE.md`, `LICENSE` and `NOTICE.md`. Copy `tools/check_palette.py` to `.baseline/check_palette.py`, outside the served tree: it is a build tool, so the site copies and pins it (the Cloudflare Pages build has only the repository, so a gate cannot run from the package itself), and never serves it. Never copy `reference/`, the other files of `tools/`, `gen_palettes.py`, `contrast-report.txt`, `site-palette.example.css` or the documents.
3. Record the baseline version and each copied file's SHA-256 in `.baseline/pin.toml` (TOML: a `version` key and a table of path to digest), `.baseline/check_palette.py` included; the site's own `site-palette.css` is not pinned. From 1.6.0 the pin covers 2 locations: the served copy folder (`assets/baseline/`), holding the runtime and licence files, and `.baseline/`, holding the build tool `check_palette.py`, which is never served. A pin gate accepts entries under either location, checks each entry's digest, and fails on a file in the copy folder that the pin does not list, on a listed file that is missing, and on any entry outside the 2 locations. Add an offline gate that fails if any copied file differs from the pin, and run that gate, the palette gate (`python3 .baseline/check_palette.py --site <name> --palettes <asset folder>/palettes.css`, with `--site-palette <asset folder>/site-palette.css` where the site has one; mandatory on every site from 1.6.0), the security.txt gate and the site's other integrity gates from the Cloudflare Pages build command, so that any failure fails the deploy. No gate reaches the network.
4. Put `class="site-<name>"` on `<html>`. That class, the logo files, the content and, from 1.6.0, an optional `site-palette.css` are the only per-site differences. A site must not add CSS that overrides `baseline.css`, with 2 exceptions:
   - an optional `site.css`, loaded after `baseline.css`, may set only the measured per-site constants `--sw` and `--logo-inset` when the site's statement or logo changes (README, "Per-site constants");
   - from 1.6.0, an optional `site-palette.css`, linked immediately after `palettes.css`, may override any palette token of section 6.1 (the 30 site tokens, 17 until 1.6.1, the rainbow tokens and `--band-grey`), light and dark, and nothing else. A site overrides a palette token only at the owner's explicit request (owner, 2026-11-03). The file uses the selectors of `palettes.css`, so that the later file wins in every state, and sets each overridden value in both forms of its scheme: light in `.site-<name>` and `[data-scheme="light"].site-<name>`; dark in `@media (prefers-color-scheme: dark) { .site-<name>:not([data-scheme="light"]) { ... } }` and `[data-scheme="dark"].site-<name>`. `site-palette.example.css` in the package is the template (1 dark `--bg` value in its 2 forms). The palette gate (item 3) fails if any pairing misses its threshold, if the 2 forms of a scheme disagree, or if the file holds anything other than palette tokens on the site's `<html>` selectors. QA for a colour change (grclibrary.ai's standard, recorded by the owner): 1 value changed in 1 file, a before and after comparison of the file and of the rendered pages showing that only the expected value changed, and the gate passing.

   A need the template cannot meet is a change request to the baseline.
5. Generate every page from the site's own sources with the markup in section 7; the reference pages are the contract.
6. Update the site's own gates where they conflict (section 11).
7. Updates arrive as 1 pull request per site that bumps the pin and the copied files; each site's own checks run as usual.
8. Add to the repository's NOTICE the site-template entry given in the package README: the template under CC0 1.0, the 4 fonts under the SIL Open Font License 1.1, and the GitHub, LinkedIn and ORCID marks under their owners' terms.

### 4.1 Staging at `/draft/` and promotion

1. **Base path.** Every page, asset and internal link is generated with a configurable base path (`/draft/` while staging, `/` after promotion), so that the draft is self-contained: no draft page links to, or loads anything from, the live pages at the root. The baseline files are copied under the draft (`/draft/assets/baseline/`) and move with it.
2. **Kept out of search and away from the live site.** Every draft page carries `<meta name="robots" content="noindex, nofollow">`; `_headers` sends `X-Robots-Tag: noindex` for `/draft/*`; the draft is absent from `sitemap.xml`, `llms.txt` and every other index the live site publishes; the live pages never link to it.
3. **Live site unchanged, with 1 exception.** Building the draft changes no live page, path, redirect or published file. The exception is the owner-ordered live hardening, which goes in its own pull request ahead of the draft: `/.well-known/security.txt`, `sitemap.xml` and the `Sitemap` line of `robots.txt`, the `apple-touch-icon` links, the removal of a live `/draft` redirect from `_redirects` (aiqt.ai and opfiles.ai carried one; every site checks), and the header changes of section 9. Nothing else changes live before promotion. A draft page may link a live file whose path is kept at promotion (for example `/downloads/*` or opfiles.ai's `/adopt.md`) rather than copying it under `/draft/`. Every existing gate keeps passing on the live tree; gates that scan every HTML file either cover the draft under the template's rules (section 11) or exclude `/draft/` explicitly, and the exclusion is removed at promotion.
4. **Review.** The draft is complete when every page of the site's page list exists under `/draft/`, the site's checks and the content guidelines checklist pass, and the implementer has reported to the owner with the draft's URL.
5. **Promotion, after the owner's approval only.** In 1 pull request: remove the old pages from the published tree (they remain in git history); rebuild the draft with base path `/`; add redirects for every old public path that changes (section 11 lists the fixed paths each site must keep or redirect); restore the root's `sitemap.xml`, `llms.txt` and other indexes for the new pages; remove the `/draft/` noindex rules and any gate exclusion; verify every fixed path on the preview deployment before merging.

## 5. Page anatomy

Every page, in this order (from `render_page()` in `build.py`):

1. `<html lang="en" class="site-<name>">`; `<head>` with `charset`, `viewport`, the page title in the form `<Page> | <Name>.ai`, `<link rel="icon" href=".../<site>-favicon.svg" type="image/svg+xml">`, `<link rel="apple-touch-icon" href=".../<site>-touch.png">`, then (from 1.6.0) `<script data-cfasync="false" src=".../scheme.js"></script>` with no `defer` or `async`, then `fonts.css`, `palettes.css`, the site's `site-palette.css` where it has one, and `baseline.css` in that order, then the page's other scripts with `defer`. A `<script type="application/ld+json">` block is data, allowed on live pages only, never on a noindex draft.
2. Skip link `<a class="skip" href="#main-content">Skip to content</a>`, first element of `body`, visible on focus.
3. `<header class="mast">`: the wordmark `a.brand` linking to the home page, then `<nav class="nav" aria-label="Site">` with the site's 4 to 6 page links on 1 row and, where the site has a public repository, GitHub as the last item (`target="_blank" rel="noopener noreferrer"` and a visually hidden "(opens in a new tab)"); the current page marked `aria-current="page"`; then, from 1.6.0, the light and dark switch `button.scheme` after the `nav` (section 7.33). No Disclosure or Licence item, nothing wraps, and no script in the links (section 7.1).
4. `<main id="main-content">`: exactly 1 `h1`; the landing page's content (section 7.2 to 7.4) or a document grid (section 7.5), which a page may set as a left-rail page with 1 side list on the left in place of the right rail (section 7.32). No breadcrumb is used in the mockups.
5. `<footer class="family wrap">`: the family footer (section 7.19).
6. `<p class="vh" id="copy-status" role="status" aria-live="polite"></p>`: the live region `copy.js` writes to.

There is no inline style, no inline script and no `on*` attribute anywhere; `build.py` refuses to write a page that contains one, or an en or em dash.

## 6. Tokens

### 6.1 Colour (`palettes.css`)

Identical names on every site, values per site and scheme: `--bg`, `--surface-raised`, `--surface-sunken`, `--text`, `--text-muted`, `--rule`, `--rule-strong`, `--accent`, `--on-accent`, `--link`, `--link-hover`, `--focus`, `--selection`, `--code-bg`, `--callout-bg`, `--glow`, `--brand`, from 1.7.0 the 13 matrix tokens `--row-tint`, `--row-hover`, `--heat-0` to `--heat-4` and `--grp-1` to `--grp-6` (below), plus `--rainbow-1` to `--rainbow-6`, `--rainbow-join-1` to `--rainbow-join-6`, `--rainbow-ink-1` to `--rainbow-ink-6` and `--rainbow-band`.

`--accent` is the text-safe form of the site's hue: it meets 4.5:1 as text, so on the yellow and orange sites in light mode it is a dark gold or burnt orange. `--brand` is the site's true rainbow colour (light: red #c9302d, orange #ec7c0e, yellow #f4c929, green #59a847, blue #136dbf, purple #9049a5) and is decorative only: the start link's underline, the Next block's rule, the figures' rule, callout and note edges, the register caption's edge, SVG arrows, the current-page cue on tags. It is never used for text.

Measured minima across all 6 sites and both modes (from the 1.6.0 `contrast-report.txt`): text 13.59:1 on the 5 surfaces and 6.78:1 on `--selection`, muted text 4.62:1, links 5.17:1, link hover 7.03:1, accent as text 4.60:1, text on accent 5.41:1, focus ring 3.14:1, strong rules 3.05:1. (Until 1.5.1 this line gave text 6.8:1, links 5.23:1, text on accent 5.44:1, focus 3.11:1 and strong rules 3.07:1, which did not match the report shipped with 1.5.1: its light values, unchanged in 1.6.0, give the minima above.)

Dark mode from 1.6.0: every dark surface and rule (the 5 surfaces, `--rule`, `--rule-strong`) takes the site's hue alone, with no warm ochre, and dark `--text` and `--text-muted` are neutral (chroma 0). The design values of dark `--bg` are OKLCH lightness 0.155 and chroma 0.030 at the site's dark hue, which is the site's own hue except for the 3 warm sites, spread apart so that they stay distinguishable (secureconfig 18, opfiles 55, auditthis 95); the emitted hex values, measured back in OKLCH: secureconfig #170707 (0.155, 0.029, hue 21), opfiles #160802 (0.154, 0.031, 53), auditthis #100c01 (0.155, 0.028, 95), cleanlanguage #060f04 (0.155, 0.029, 139), aiqt #040d19 (0.156, 0.030, 253), grclibrary #110814 (0.154, 0.029, 318). The closest pair, red and orange, measures 1.64 apart (OKLab distance x 100). The other dark surfaces keep their 1.5.1 lightness steps from `--bg` (raised +0.05, sunken -0.045, code -0.05, callout +0.065 with chroma 0.040, rule +0.145), every surface chroma scaled by the same factor. Light mode is byte-identical to 1.5.1.

Matrix tokens from 1.7.0 (owner, 2026-11-04), new tokens only: every token above keeps its 1.6.1 value in both schemes (`palettes.css` is byte-identical to 1.6.1 once the 312 new lines are removed). Each tint is a surface that text sits on, so `gen_palettes.py` tunes it from a design lightness towards `--bg` until the text on it passes.

- `--row-tint` (the zebra stripe) and `--row-hover` (the hovered row and the highlighted column): `--text`, `--text-muted`, `--link`, `--link-hover` and `--accent` at 4.6:1 or more, `--focus` at 3.1:1 or more. Measured minima across the 6 sites: light 4.60:1 (accent on `--row-hover`), muted text 4.62:1, focus 3.12:1; dark muted text 5.82:1, accent 5.50:1, focus 5.87:1.
- `--heat-0` to `--heat-4` (the heat ramp, section 7.34): a heat cell's own text is `--text` and its count may be a link, so each step is tuned for `--text`, `--link` and `--link-hover` at 4.6:1 and `--focus` at 3.1:1; `--text-muted` and `--accent` are never drawn on a heat step (the stylesheet sets a heat cell's muted lines to `--text`). Measured minima: light links 4.91:1, focus 3.10:1; dark links 5.26:1, focus 4.97:1. The dark steps grow in chroma and depth from design values and measure 3.0 to 3.8 apart (OKLab distance x 100). The light ramp is spread as far as the checks allow (owner, 2026-11-04): `--heat-0` is white, `--heat-4` is the colour at the site's hue farthest from it that passes every heat check (searched over lightness and chroma), and `--heat-1` to `--heat-3` sit at equal OKLab steps between them, each checked. The focus ring's 3:1 on `--heat-4` is the binding limit (3.10:1 to 3.11:1). Adjacent light steps measure: secureconfig 2.2 to 2.3, opfiles 1.9 to 2.1, auditthis 2.9, cleanlanguage 4.5 to 5.5, aiqt 1.8 to 2.1, grclibrary 2.3 to 2.6 (the 1.6.0 changelog takes about 2 as the side-by-side difference most readers notice). The printed count carries the value; the shading reinforces it.
- `--grp-1` to `--grp-6` (column-group accents, section 7.34): the family's 6 hues in the order of section 1, each tuned as text on that site's 5 surfaces and 2 row tints at 4.6:1. Measured minima: light 4.60:1, dark 6.30:1.

`contrast-report.txt` lists every pair per site and scheme, with the heat step distances; 0 pairs fail.

A site may override these tokens only as section 4, item 4 sets out.

## 7. Components

Each component has 1 required markup pattern; the reference pages carry them in full. Class names are kept as built (no `bl-` prefix), because the mockups, the gates and this document all use them.

### 7.1 Top bar and wordmark

Markup: `<header class="mast"><a class="brand" href="/"><span class="name">Name<span class="tld">.ai</span></span><span class="rule" aria-hidden="true"></span></a><nav class="nav" aria-label="Site"><a href="...">Page</a>...<a href="https://github.com/..." target="_blank" rel="noopener noreferrer">GitHub<span class="vh"> (opens in a new tab)</span></a></nav></header>`. The name is the site's word in Public Sans 700 with the `.ai` in `--gold` and a 3px rule in `--gold-rule` beneath.

The bar is a grid of the wordmark, the links and, from 1.6.0, the light and dark switch (section 7.33), and never wraps. `nav.nav` holds the site's own 4 to 6 page links on 1 row, right-aligned, tracked uppercase in `--text-muted` (the current page in `--accent`), the size scaling with the window between 0.66rem and 0.74rem; GitHub is the last, right-most item where the site has a public repository; Disclosure and Licence are not in the bar (section 7.24). When the row cannot hold the links it scrolls sideways (`overflow-x: auto`, thin scrollbar) and a shadow appears at the edge where links continue, drawn with `background-attachment: local` gradients (`color-mix` of `--rule-strong` with transparency) and no script; the shadow shows only on the overflowing side and disappears when the row is scrolled to that end. Measured in the reference pages: at 1180 and 1512 px every site's links fit on 1 row with no scrolling (6 links plus GitHub on the widest); at 1000 px and below the wordmark takes the first row and the links a full-width second row, left-aligned, still 1 row, with no scrolling at 820 on any reference page. Measured on the 1.6.0 reference pages at 390 px, with the fonts loaded: the row scrolls by 0 px on grclibrary.ai's pages with 4 short links and GitHub (44 px on its 404 page, whose links are longer), 55 to 100 px on the pages with 4 links and GitHub, 163 px with cleanlanguage.ai's 6 links and 206 px with auditthis.ai's 5 long links. The 1.5.1 pages give the same values; until 1.5.1 this section gave about 130 px with 6 links and none with 4, which these measurements do not reproduce. The switch sits outside the scrolling row and does not change it at any width (measured at 390, 820, 1000, 1180, 1512 and 2000 px: every reference page's row scrolls by the same amount as in 1.5.1). The bar is 71 px tall at 1180 px and 112 px at 390 px, as in 1.5.1.

### 7.2 Hero

Markup: `<section class="hero" aria-label="Introduction"><div class="hero-text"><p class="lbl gold">kicker</p><h1 class="statement">... <em>emphasized ending</em></h1><p class="intro">...</p><a class="start" href="...">Start text <span class="arrow" aria-hidden="true">&rarr;</span></a></div><div class="hero-art"><img src="logo.svg" alt="..."></div></section>`. The hero is a 2-column grid: the text block, then the logo column of width `--art`, right-justified over a radial glow (`--glow`), with a right margin of half the logo width (`padding-right: max(0px, calc(var(--art) * 0.5 - var(--pad)))`) so that the logo's margin equals half its width at every width where that exceeds the gutter. The logo fades in over 400 ms unless the reader prefers reduced motion.

The statement: 1 sentence with an emphasized ending (`<em>` in `--accent`, italic, never split), or 2 sentences with the second in `<em>`; a 2-sentence statement carries `class="statement two"`. The size is `clamp(2.6rem, 98cqw / var(--sw), 5rem)`: the statement fills 98 % of the text column on 1 line whenever that gives 2.6rem or more, and never drops below the floor; below the floor the `em` moves whole to a second line. `--sw` is the statement's 1-line width in em, measured per site and scheme (dark mode adds 0.01em of tracking): secureconfig 13.712 light and 14.612 dark; opfiles 15.070 and 16.070; auditthis 12.562 and 13.337; cleanlanguage 12.824 and 13.724; aiqt 19.868 and 21.218; grclibrary 13.069 and 13.894. A site that changes its statement must re-measure `--sw` (render the statement at 100px with `white-space: nowrap` and divide its width by 100). At 1000 px and below the floor is 2.4rem and the cap 3.2rem; at 600 px and below the size is 2.2rem, the grid becomes kicker beside a 5.5rem logo with the title, introduction and start link full width, and a 2-sentence statement's `em` becomes a balanced block.

The introduction is at most 3 sentences and about 60 words (content guidelines section 2). aiqt.ai's hero carries the priority ordering as `<span class="ordering">` inside the introduction.

### 7.3 Entry tiles ("Start here")

Markup: a labelled region (section 7.5) whose content is `<ol class="entries"><li><a href="..."><span class="t">Title</span><span class="n">metadata</span><span class="d">1 line</span></a></li>...</ol>`, 3 to 6 items. Each tile is a vertical stack: the numeral (CSS counter, Newsreader 300 2.3rem in `--accent`), the title (Newsreader 600 1.4rem), the metadata (JetBrains Mono 0.8rem, `--text-muted`) directly under the title, then the description (Public Sans 1.05rem). The tiles form 1 row of equal columns (`grid-auto-flow: column`) read left to right; with 5 or more items the title drops to 1.2rem and the description to 0.95rem (`:has(li:nth-child(5))`). At 1000 px and below the list is 1 vertical sequence with the numeral beside its own title.

### 7.4 Value paragraph ("What it gives you")

Markup: a labelled region with the label "What it gives you" and `<p class="value">...</p>`, measure 68ch, body size. Under 100 words (the mockups run 81 to 91), written for a capable non-developer, building on the introduction, ending with 1 plain sentence of the material facts; the licence link sits inside it (for example "free to use under CC0"). It replaces Benefits and gaps; fuller scope statements live on the relevant inner page as a Scope paragraph (section 7.14). Content guidelines section 7 governs the wording.

### 7.5 Labelled regions and the document grid

Regions: `<div class="region"><p class="lbl">Label</p><div>content</div></div>`, a 2-column grid of label column (9rem) and content; the landing page's "Start here" and "What it gives you" are regions. Document pages: `<div class="doc">` holding, in order, `<p class="lbl first">kicker</p>`, `<h1>`, the rail (section 7.6), an optional `<p class="meta">` line (Public Sans 1.05rem, 66ch), then blocks. Every direct child sits in the text column except `.lbl` (label column; `.lbl.sec` precedes an `h2`, `.lbl.blk` precedes a block, `.lbl.accent` in `--accent`), `.rail` (rail column, sticky at 1.5rem from the top), `.wide` (text column, used for tables and figures) and `.full` (all 3 columns). `section` and `article` children use `display: contents` so their children take the grid. Text blocks have a measure of 72ch. At 1000 px and below the grid is 1 column with labels above their content.

### 7.6 Rail

Markup: `<nav class="rail" aria-label="On this page"><img class="rail-logo" src="logo.svg" alt="..."><p class="lbl">On this page</p><ol><li><a href="#id">Section</a></li>...</ol></nav>` on a page with sections worth listing, with `<script src=".../rail.js" defer></script>` on that page; no link carries `aria-current` in the markup. `rail.js` marks the link of the section the reader is on with `aria-current="location"` (the WAI-ARIA token for the current location within a set): the last section whose top has passed a line a quarter of the viewport down; at the end of the page, the last section in view; after a rail click or on a page opened at `#id`, that section. While the script runs, at most 1 link is marked, and exactly 1 once a listed section has reached the screen; before that (a page opened at the top whose first section starts below the screen, as on phones where the rail sits inline above a long introduction) no link is marked, which is accurate: the reader is still in the introduction. Without script no link is marked. The CSS colours `[aria-current="location"]` and, for pages built on 1.2.1 and earlier, `[aria-current="true"]`, which `rail.js` clears on load; `<div class="rail"><img class="rail-logo" ...></div>` (logo only) on any other page, including the licence and 404 pages. The list is numbered by CSS counter in `--accent`; it is the page's own sections and never the site menu. The logo fills the rail width; the label and list are indented by `calc(100% * var(--logo-inset))`, where `--logo-inset` is the logo artwork's visible left margin as a fraction of the SVG box (secureconfig 0.115, opfiles 0.1225, auditthis 0.2075, cleanlanguage 0.185, aiqt 0.0975, grclibrary 0.115; measured by rendering each logo at 400 px), so the text starts under the artwork's left edge within 0.1 px. At 1000 px and below the rail sits under the `h1`, the logo is capped at 7rem, the indent becomes `calc(7rem * var(--logo-inset))` and the list runs in 2 columns (1 column at 600 px and below).

### 7.7 Document control strip (aiqt.ai)

Markup: `<dl class="control"><div><dt>Document</dt><dd>aiqt.ai</dd></div><div><dt>Version</dt><dd>AIQT 1.0.5</dd></div><div><dt>Status</dt><dd>...</dd></div><div><dt>Source</dt><dd><a ...>jposluns/guardrails</a></dd></div><div><dt>Licence</dt><dd><a href="/license/">Apache 2.0, see NOTICE</a></dd></div></dl>`, placed after the meta line on every inner page. JetBrains Mono 0.8rem, uppercase `dt`, hairlines above and below in `--rule-strong`, wrapping as needed. The version and status must come from the repository's `VERSION` and its own published wording.

### 7.8 Numbered clauses (aiqt.ai)

### 7.29 Search and facets

Section 7.13 gives the form and the list; this section gives the options of `search.js` from 1.5.0, each opt-in by markup. They are a separate section because they add a contract of their own (attributes, address parameters, status wording), and 7.13 stays the index-list component. Reference pages: `search.html` (results mode with facets) and `facets.html` (default mode with facets).

- **Default mode, unchanged from 1.4.1.** An empty query shows every row and leaves the status empty; a query shows the rows whose `data-search` text (or, without it, the row's text) holds every term, and the status reads "N of M documents match.". On a page without facets this wording stays. A page on 1.4.1 markup behaves as before: measured on grclibrary.ai's mockup search page (36 rows) for 12 queries, the hidden rows, the row order and the status text are identical under the 1.4.1 and 1.5.0 scripts.
- **Results mode.** `data-search-mode="results"` on the scope: with an empty query and no active facet no row shows, and the status shows a prompt, `data-search-prompt` on the scope or "Type to search the documents."; a query, or an active facet, shows only the matching rows.
- **Title ranking.** On in results mode, and in default mode with `data-search-rank="title"` on the scope: among the matching rows, those whose title holds every term come first, and each group keeps page order. The title is the row's `data-title`, or else the text of its first `a` without any `.vh` text. Clearing the query restores page order. Ranking moves rows within their own list only.
- **Facets.** A chip group is any element with `data-filter-group="<group>"` (lowercase letters, digits and hyphens; never `q`), usually `<ul class="chips">`, holding links or buttons with `data-filter="<value>"`; `data-filter=""` is the group's All chip. Each row carries `data-<group>`, a space-separated list of values (for example `data-fw="iso27001 csf"`). 1 value per group is active; a second click on the active chip, or a click on All, clears the group. A row shows when every active facet's value is among its tokens and it matches the query. Values compare in lowercase. The chosen chip carries `aria-pressed="true"` and the others `"false"` (All is pressed when its group is clear). Because `aria-pressed` belongs to buttons, the script gives a link chip `role="button"` and makes the space key activate it, as a toggle; a modified click (a new tab or window) is left to the browser, so the link still works, and without script every chip is a plain link to a real page. Rows are hidden with the `hidden` attribute. On a page with facets the status reads "Showing N of M documents.".
- **The address.** On load, `?q=` fills the input and `?<group>=<value>` sets a facet (a value with no chip in that group is ignored). As the reader types or clicks, the script writes the state back with `history.replaceState`, removing a parameter whose value is empty and keeping every other parameter and the hash; no history entry is added. This applies in both modes: in default mode it changes no row and no status for a given query, and a page on 1.4.1 markup had no use for a `q` parameter, so it is not opt-in.
- **Without script** every row shows, every chip is a plain link and the input does nothing, as in 1.4.1.
- **Chips that would show nothing (from 1.7.0, grclibrary.ai's request, owner, 2026-11-04).** Opt-in per group, on the group's element: `data-filter-empty="disable"` and, optionally, `data-filter-count="live"`; any other value counts as absent, and a page with neither on any group runs as in 1.6.1 (measured: the DOM and the address after the same 7 actions are identical under the 1.6.1 and 1.7.0 scripts on `search.html` and on `facets.html` with the attributes removed, 32 of 32 snapshots). The served HTML is unchanged; only the script sets the new attributes.
  - *Would-show count.* Recomputed on load, on every input and on every chip choice: for each chip of an opted-in group, the rows that hold every query term, the chosen value of every other group and the chip's value (the chip's own group's choice is ignored, because choosing replaces it); for All, without this group's condition. A row with several values in a group counts toward each. At load the script prepares each row's lowercased text and group tokens once; each update is 1 pass over the rows, finding which conditions a row fails: none, and it counts toward its values in every group and every All; only 1 group's, and it counts toward that group's values and All; the query, or 2 or more groups, and it counts nowhere. The DOM changes only where a chip's state or count changes.
  - *Unavailable chip.* With `data-filter-empty="disable"`, a chip whose count is 0 takes `aria-disabled="true"` (never the `disabled` attribute), loses it when the count rises, and stays in the tab order. All is never unavailable, nor is a chosen chip, even when the result is empty, so a click can still clear it; the script never drops a choice by itself. Activating an unavailable chip (a click, Enter on a link, Space through the chip's key handler) changes no choice, row or address, and the status reads "<Chip label> would show no documents with the current choices." until the next change; focus stays on the chip. A modified or middle click is left to the browser, as in 1.6.1. Each unavailable chip points through `aria-describedby` to 1 note per page, `<p id="filter-empty-note" hidden>Would show no documents with the current choices</p>`, created by the script; the note carries `hidden` so that it is never read as page text on its own, while a description is still computed from it. There is no live announcement per chip; the result stays in the status, "Showing N of M documents.".
  - *Look.* `.chips [aria-disabled="true"]`: a dashed border in place of the solid one, `cursor: not-allowed`, and no hover change; the text and border keep the chip's colours (`--text-muted`, `--rule-strong`), with no fading and no transition. The 1px dashed border in `--rule-strong` measures at least 3.05:1 on the page background on all 6 sites, in the 6 states of section 6.1 (device light or dark; no `data-scheme`, `light` or `dark`), so no 2px border is needed.
  - *Live counts.* With `data-filter-count="live"`, each chip's `.n` text becomes its would-show count (an unavailable chip reads 0, a second cue in text); without it `.n` keeps its served count. A page whose text says the counts never change must say otherwise.
  - *Results mode.* Counts ignore the rule that no row shows until the reader types or picks a chip, so on an idle results page a chip is unavailable only when no row holds its value; ranking does not affect counts.
  - *The address.* Read and written as in 1.5.0; a refused value is never written. A link that opens on an empty combination keeps its values: the chosen chips stay selected and available, the list is empty, and the status reads "Showing 0 of M documents.".
  - Reference page: `facets.html`, whose Domain group is opted in, Type group opted in with live counts, and Framework group left as in 1.6.1. Measured in Chromium 153 (headless, Playwright): 51 checks, 0 failing, 0 console errors (the request's checks 1 to 5; 26 page states compared chip by chip against counts computed independently from the rows; results mode; the look; tab order). Not tested: screen readers (NVDA, JAWS, VoiceOver), the request's check 6. Speed on a page of 3,000 rows with 3 groups of 20 chips, all opted in with live counts, headless Chromium on the build machine, the median of 14 typed updates: 1.8 ms for the script and 7.6 ms with style and layout; with the CPU throttled 4 times through the DevTools protocol, 10.5 ms and 40.4 ms (the same page without the attributes: 12.5 ms and 36.7 ms). These are headless measurements, not a phone.

### 7.30 Matrix with presets

Markup: presets as links (recommended, so that each leads to a page that resolves without script) or buttons, anywhere on the page, each with `data-preset="<key> <key> ..."` (the column keys it shows) and `data-preset-id="<id>"` (its name in the address); the All preset has `data-preset=""` and shows every column. `<p class="matrix-status" role="status" aria-live="polite" data-matrix-status></p>` above the table. The table: `<div class="tablewrap bounded" tabindex="0"><table class="matrix sticky sticky-col" data-matrix><caption class="vh">...</caption><thead><tr><th scope="col">Domain</th><th scope="col" data-col="<key>">Name<span class="org">Organization</span></th>...</tr></thead><tbody><tr><th scope="row">Row</th><td data-col="<key>"><code>id</code><a href="...">count<span class="vh"> documents</span></a></td>...</tr></tbody></table></div>`. 1 matrix per page.

`matrix.js` shows the chosen preset's columns and hides the others with the `hidden` attribute on their `th` and `td`; the row-header column carries no `data-col` and always shows. The status names the preset and the columns shown ("View: Security programmes. Showing 4 of 8 columns."). The chosen preset carries `aria-pressed="true"` when it is a button (the others `"false"`) and `aria-current="true"` when it is a link (the others none): a preset choice is a choice of view among links, so a link keeps its link role and is marked as the current item of its set, as the install selector does (section 7.12); `aria-pressed` is not valid on a link. `?view=<id>` chooses a preset on load (an unknown id is ignored, and the All preset is chosen); a choice is written back with `history.replaceState`, and All removes the parameter. A modified click is left to the browser. Without script every column shows and each preset is a plain link (grclibrary.ai points them at its per-preset static pages). The table has a single header row by design, so the script has no `colspan` handling: a matrix with grouped or spanning headers is out of contract. Cells hold short identifiers and count links only, never third-party control text. Reference page: `crosswalk.html`.

From 1.7.0 the script has 2 more options, each opt-in by markup; a page without them behaves exactly as above (the 1.5 and 1.6 matrix checks, 54 of 54, pass unchanged on `crosswalk.html` 1.7.0).

- **Column toggles.** `<div class="matrix-toggles" data-col-toggles hidden>` holding 1 `<button type="button" data-col="<key>" aria-pressed="true">` per column, optionally in groups, each a `<p class="lbl" id="...">` naming the group and a `<div class="chips" role="group" aria-labelledby="...">` of buttons. Without script the container keeps `hidden` and every column shows. The script reveals it. A press shows or hides that column, setting `hidden` on its `th`, its `td` and any `col` with the same `data-col` (in a fixed-layout table a column's width comes from its `col`, so a hidden column hides its `col` too); `aria-pressed` follows; focus stays on the pressed button; nothing animates. The status reads "Showing N of M columns.", or, when the columns shown are exactly a preset's, that preset is chosen and the status keeps the preset wording. Presets and toggles stay in sync both ways. The pressed state is shown by `aria-pressed` and the chips' 2px accent border, not by colour alone.
- **The address.** A set of columns that is a preset's is written as `?view=<id>`; any other set as `?cols=<key>+<key>` (space-separated keys, so `+` in the address) with `?view=` removed; all columns removes both, with `history.replaceState`, as for presets. `?cols=` is read on load only on a page with toggles; unknown keys are ignored, and with no known key `?view=` applies. This keeps 1 parameter per state and the preset form for any set a preset names.
- **Column highlight.** `data-col-highlight` on the table: while the pointer is over a cell, or keyboard focus is inside one, every cell sharing its `data-col` (the header cell included) takes the class `colhl`, drawn in `--row-hover`, and loses it on leaving. Focus is never moved, and the row-header column has no `data-col` and is never highlighted. A heat cell keeps its step. Reference page: `matrix.html`.

### 7.31 Sticky scroll box

A sticky header can stick only to its nearest scroll container, and `.tablewrap` is one, so until 1.5 the header of a `.sticky` table stuck to an unbounded wrapper and left the screen with the page. Markup from 1.5.0: `<div class="tablewrap bounded" tabindex="0"><table class="sticky [sticky-col]">`. `.tablewrap.bounded` is a box at most 75 % of the viewport height (`75svh` where supported, `75vh` otherwise) that scrolls in both directions, with `overscroll-behavior: contain`; inside it the header row stays at the box's top. `table.sticky-col` keeps the first column at the box's left edge. From 1.7.0, opt-in, `table.sticky-col.pin-cap` gives the first column a capped width, `clamp(8rem, 30vw, 15rem)`, and lets its text wrap, so a long row label cannot take most of a phone screen; the first column's `th` holds the row's name, not a paragraph. `--pin-col` overrides the width, set by a class on the table: `pin-r6` and `pin-r8` (6rem and 8rem), and `pin-r10` to `pin-r20` in steps of 2 (`clamp(8rem, 30vw, Nrem)`, so they change only the cap). In a fixed-layout table, leave the first `col` without a width class, so that the cap sets the width. `table.sticky-col` without `pin-cap` renders exactly as in 1.6.1 (owner, 2026-11-04): measured on `crosswalk.html`, which does not use the class, the pinned column is 109, 109, 117 and 143 px at 320, 390, 1280 and 1512 px in both versions, with the same row heights. Sticky cells take the page background (`--bg`), or from 1.7.0 the row's opaque tint (section 7.34), so scrolled content never shows through, and the stacking order is the first column 1, the header row 2 and the top-left cell 3, so the corner sits above both. A sticky table uses separated borders with no spacing, so the header hairline moves with the header. Markup built on 1.4.1 (`.tablewrap` holding `table.sticky`, without `.bounded`) is bounded through `.tablewrap:has(> table.sticky)`, in a rule of its own so that a browser without `:has()` still applies the `.bounded` rule and renders the 1.4.1 markup as before. Measured in Chromium 153 (headless, Playwright) at 390, 820, 1180 and 1512 px in light and dark: after a page scroll that puts the box's top 100 px below the window's top and an inner scroll of 500 px down and 300 px across, the header row's top equals the box's top, the first column's left edge equals the box's left edge, the top-left cell is the topmost element at its position, and the page does not scroll sideways. Support in other browsers was not tested. The box is bounded by design: when the page is scrolled past the box's top, the header leaves the screen with it. 75 % leaves a quarter of the window outside the box at every height, so the reader can always scroll the page past it. From 1.5.0 `.tablewrap` is also `position: relative`, so visually hidden text inside a cell stays inside the box and cannot widen the page.

### 7.33 Light and dark switch

From 1.6.0, on every page, the 404 page included. Markup, the last child of `header.mast`, after `nav.nav`:

`<button class="scheme" type="button" data-scheme-toggle aria-pressed="false" hidden><svg class="moon" viewBox="0 0 24 24" width="24" height="24" fill="none" stroke="currentColor" stroke-width="1.8" stroke-linecap="round" stroke-linejoin="round" aria-hidden="true" focusable="false"><path d="M20.5 14.2A8.5 8.5 0 0 1 9.8 3.5a8.5 8.5 0 1 0 10.7 10.7z"/></svg><svg class="sun" ...><circle cx="12" cy="12" r="4.2"/><path d="M12 2.5v2.2M12 19.3v2.2M2.5 12h2.2M19.3 12h2.2M5.3 5.3l1.6 1.6M17.1 17.1l1.6 1.6M5.3 18.7l1.6-1.6M17.1 6.9l1.6-1.6"/></svg><span class="vh">Dark mode</span></button>`

with `<script data-cfasync="false" src=".../scheme.js"></script>` in `<head>`, before the stylesheets, with no `defer` or `async` (the reference pages carry the full markup of both glyphs). The 2 glyphs are drawn for the package in inline SVG with presentation attributes only, so the CSP needs no change and no icon set is loaded.

- **Place.** The 3rd column of the top bar, after the links and GitHub, outside the scrolling `nav`, so it never scrolls away. At 1000 px and below it sits at the right of the wordmark's row, above the scrolling links. Its right margin of -0.625rem lines the glyph up with the page gutter; its block margins of -0.25rem keep the bar at its 1.5.1 height. The gap after the wordmark is the wordmark's margin (0 at 1000 px and below, where the wordmark has its own column), so the 3rd column takes no space when the button is absent or hidden: the 1.5.1 pages on the 1.6.0 stylesheets and the 1.6.0 pages without script lay out the bar exactly as 1.5.1 (measured on the 14 reference pages at 6 widths from 390 to 2000 px).
- **Look.** A 24 px glyph in a 44 by 44 px target (larger than the 24 px that section 10 requires outside the footer), `--text-muted` at rest and `--text` on hover, the standard focus ring. The glyph shows the scheme a press leads to: a moon while light shows, a sun while dark shows; CSS chooses it from `prefers-color-scheme` and `data-scheme`, so it is right before the script has run.
- **Name and state.** The accessible name is "Dark mode" (visually hidden text); `aria-pressed` is `"true"` while dark shows and `"false"` while light shows, whether the scheme comes from the device or from a press. This is the toggle button of the WAI-ARIA Authoring Practices button pattern (https://www.w3.org/WAI/ARIA/apg/patterns/button/, read 2026-11-03), which says that "it is critical the label on a toggle does not change when its state changes"; the glyph changes with the state and the name stays the same.
- **Behaviour.** Until the reader presses it, the page follows the device setting and the button follows device changes. A press sets `data-scheme="light"` or `"dark"` on `<html>` (the attribute `palettes.css` and `baseline.css` already honour; `color-scheme` follows it, so scrollbars and form controls match) and stores the same value in `localStorage` under the key `scheme`. On a later page `scheme.js` reads the stored value and sets the attribute while `<head>` is parsed, before the first paint, so the page never shows the other scheme first; the same file wires the button once the DOM is ready (1 file: the part that must run early is 2 lines, and a second request would buy nothing). Every storage access is wrapped in `try`, so blocked storage leaves the switch working for the current page. A stored choice that equals the device setting stays stored, because the reader chose it. There is no 3rd "automatic" state: a reader who never presses the switch keeps the automatic behaviour, and offering a way back to it would need a 3-state control in place of a 2-state button, which the owner did not ask for; clearing the site's storage restores it.
- **Without script** the button keeps its `hidden` attribute and is never shown, so no reader sees a switch that does nothing; the page follows the device setting as in 1.5.1.
- **Cloudflare.** `data-cfasync="false"`, placed before `src`, keeps Rocket Loader from deferring the file (Cloudflare's documentation, https://developers.cloudflare.com/speed/optimization/content/rocket-loader/ignore-javascripts/, read 2026-11-03: the attribute "must be added before the `src` attribute"). Not tested: if Rocket Loader deferred the file, the stored scheme would apply only after the page had painted in the device scheme. A site gate that allows only certain attributes on an external `<script>` must admit `data-cfasync="false"` on the `scheme.js` element, placed before `src`. A `data-*` attribute does not change whether or how a browser runs the script; only Cloudflare reads it.

Measured in Chromium (headless, Playwright) on the 14 reference pages, device light and dark: 588 checks, 0 failing (button shown at 44 by 44 with a 24 px glyph; a press toggles `data-scheme`, `aria-pressed`, `color-scheme` and the colours; after a reload the attribute is set before `<body>` is parsed and `--bg` already has the stored scheme's value at the first animation frame and at `DOMContentLoaded`; device changes followed while nothing is stored; with `localStorage` replaced by a getter that throws, no error and the switch works; without script the button has no box; Tab reaches it after the top bar's links (8 or 9 presses from the top of the page), and Enter and Space toggle it; at 390 px it stays in place while the links scroll). Other browsers were not tested.

### 7.34 Large matrix tables

From 1.7.0 (owner, 2026-11-04, the table request for crosswalk pages, parts 1 and 2). Every capability is opt-in by a class or an attribute. Reference page: `matrix.html`, 10 domains by 20 instruments with every capability below; its instrument names and organizations are real, and its groups, identifiers, counts and shading are illustrative sample data.

**The combined form.** This is the accessibility contract for a large matrix:

```html
<p class="matrix-status" role="status" aria-live="polite" data-matrix-status></p>
<div class="tablewrap bounded" tabindex="0" role="region" aria-label="Sample matrix: 10 domains by 20 instruments">
<table class="matrix fixed sticky sticky-col pin-cap cells-wrap zebra rowhover" data-matrix data-col-highlight>
<caption class="vh">Sample matrix: 10 domains by 20 instruments, in 4 groups</caption>
<colgroup><col><col class="r12" data-col="iso27001"> ... <col class="r6" data-col="dora"></colgroup>
<thead><tr><th scope="col">Domain</th>
<th scope="col" data-col="iso27001" data-grp="1">27001<span class="org">ISO/IEC</span><span class="grp">Security</span></th> ...
<th scope="col" class="rot" data-col="dora" data-grp="4">DORA<span class="org">EU</span><span class="grp">Resilience</span></th></tr></thead>
<tbody><tr><th scope="row">Governance</th>
<td data-col="iso27001"><code>EX.1.1</code> <code>EX.1.1a</code><a href="...">3<span class="vh"> documents</span></a></td>
<td class="na" data-col="csf">none</td> ...
<td class="nowrap" data-col="dora" data-heat="2"><a href="...">4<span class="vh"> documents</span></a></td></tr> ...
</tbody></table></div>
```

The wrapper is focusable (`tabindex="0"`), a named region (`role="region"` with an `aria-label` naming the table), so keyboard users can reach the box and scroll it with the arrow keys, and the standard `:focus-visible` ring shows where they are. Column headers carry `scope="col"` and row headers `scope="row"`. A `caption` (visible or `.vh`) or a heading before the table names the matrix. The top-left cell sits above both pinned axes (stacking order: first column 1, header row 2, corner 3) on an opaque background. Sticky positioning never changes the DOM order, so screen readers read the table in source order.

- **Column widths in rem (1.1).** In a `table.fixed`, `col.r6` to `col.r24` in steps of 2 set a per-column custom property, `--colw`, and 1 rule, `.fixed col { width: var(--colw); }`, applies it; a `col` without one of these classes leaves `--colw` unset, so its width stays `auto`, and the `col.w<N>` percentages keep their higher-specificity rules. The choice: inline `style` is forbidden by the CSP (`style-src 'self'`) and by section 12, so a per-column value must come from markup that the stylesheet maps; classes on `col` are already the pattern of `col.w<N>`, and a `data-colw` attribute would need the same 10 mapping rules. In fixed layout the table's width is the larger of its `width` and the sum of its columns, so a matrix whose columns add up to more than the page grows past it and scrolls inside `.tablewrap`. Use rem classes or percentages in 1 table, not both. Measured: 96, 128, 160, 192, 224, 256, 288, 320, 352 and 384 px for `r6` to `r24` at the 16 px default; on `matrix.html` the table is 3312 px wide in an 866 px box at 1180 px, with no page overflow at 320, 390, 820, 1180, 1512 or 2000 px.
- **Wrapping cells (1.2).** `table.matrix.cells-wrap`: data cells wrap within their column (`white-space: normal`, identifiers in `code` included); headers keep their rules. `td.nowrap` keeps a cell on 1 line, for example a count-only column, and `td.id` keeps its own rule. Measured on a test table with 10rem columns: a wrapping cell of 4 identifiers and a count runs to 2 lines (68 px), a `td.nowrap` cell stays on 1 line (44 px).
- **The pinned column (1.3).** Section 7.31: `table.sticky-col.pin-cap`, `clamp(8rem, 30vw, 15rem)`, `--pin-col` through the `pin-r<N>` classes, labels wrap. The 8rem minimum keeps at least half of the window for data on phones (owner, 2026-11-04: half of the window, not of the box). Measured on `matrix.html` as the data visible in the window, from the pinned column's right edge to the box's right edge: at 320 px the pinned column is 128 px (right edge at 144 px) and the data area 160 px, 50.0 % of the window; at 360 px 200 px, 55.6 %; at 390 px 230 px, 59.0 %.
- **Row guides (1.4).** `table.zebra` tints even body rows with `--row-tint`; `table.rowhover` tints the row under the pointer with `--row-hover`. The tint applies to every cell of the row, the sticky `th` and `td` included, and the tints are opaque, so a pinned cell keeps the row's colour and scrolled content never shows through. No transition. Hover is a reading aid only and does nothing on touch, which loses nothing.
- **Empty cells (1.5).** `<td class="na">none</td>`, with the site's own word: muted (`--text-muted`), centred, the word kept in the cell so that screen readers and copied text get the same answer as sighted readers. It passes 4.5:1 on every surface and row tint (section 6.1).
- **Heat shading (2.2).** `td[data-heat="0"]` to `"4"` in a `table.matrix`, mapped to `--heat-0` to `--heat-4`, 1 ramp per site and scheme. The count stays printed in the cell, so colour is never the only carrier; a heat cell's own text is `--text` and its links keep `--link`, the colours each step is checked against. A heat cell keeps its step under the row and column tints. The mapping from a count to a step is site logic. The legend: `<ul class="chips heat-legend" aria-label="..."><li><span class="tag" data-heat="0">1 document</span></li> ... </ul>`, each step named in words on its own shading. Heat drops to white in print.
- **Rotated headers (2.4).** `th.rot` sets the header text vertically, read from the bottom up, with `writing-mode: sideways-lr` where the browser supports it and `vertical-rl` (read from the top down) where it does not; it is capped at 11rem and wraps to a 2nd line beyond that. There is no transform: rotating the cell would also move its header hairline to the top. The text is unchanged, so screen readers read it as written. For a short visible form, put the full name in a `.vh` span in the same `th`, for example `CCM<span class="vh"> (Cloud Controls Matrix)</span>`, so every reader gets the full name; never a `title` attribute as the only carrier.
- **Column groups (2.6).** `data-grp="1"` to `"6"` on `thead th` draws a 3px accent under the header cell in `--grp-1` to `--grp-6` (the family's 6 hues, each text-safe on the site's surfaces), and `<span class="grp">Group</span>` in the header cell names the group in the same colour. The group is named in text (the tag line, and the toggle group's label where there are toggles); the colour reinforces it.
- **Print (2.5).** In `@media print`, for `table.matrix`: the bounded box loses its height cap and inner scroll, so the whole matrix prints; sticky cells are static; `thead` repeats on each page and rows do not split; the column toggles and the presets are hidden; every cell, and the links, identifiers and tag lines in it, is black (`--print-ink`) on white (`--print-paper`), with no tint or heat. The rules apply to `table.matrix` only: another bounded table keeps its screen rules in print, so it prints only its visible part (measured on `reference.html`: the register's box prints 675 px of a 1219 px table, as in 1.5.0 to 1.6.1).
- **Accessibility.** Every colour comes from palette tokens, with text at 4.5:1 in both schemes (section 6.1); nothing depends on colour alone (counts, words and group names are text); no rule in this section has a transition or an animation, so there is no motion to reduce (a future one must respect `prefers-reduced-motion`); hover and the column highlight are reading aids, and nothing exists only on hover.

Measured in Chromium 153 (headless, Playwright) on `matrix.html` and a test table: 90 checks, 0 failing, 0 console errors (widths at 7 window widths in both schemes; stripes and hover on sticky cells; contrast read from the rendered page for `td.na`, heat cells and legend, text on the row tints and the group tags, on all 6 sites in both schemes, lowest 4.62:1 (heat cells 4.91:1); rotated headers; print emulation; toggles, the address and the highlight; no script). Print emulation renders 1 long page, so page breaks and the header row repeating on paper were not observed; the stylesheet sets `thead` to `table-header-group` and `break-inside: avoid` on rows. Other browsers were not tested.

## 12. Code style

- HTML: lowercase elements and attributes, double quotes, root-relative asset paths, semantic elements before `div`, `lang="en"`, no inline style or script, no `on*` attributes; every external link carries `target="_blank" rel="noopener noreferrer"` and a visually hidden "(opens in a new tab)".
- CSS: colour from tokens only (no literal colours outside `palettes.css` and a site's own `site-palette.css`, except the family tokens in section 6.2 and `--band-grey` until it moves); rem, ch, cqw and percentage units; no `!important` except the `.vh` utility; comments in plain English without dashes.
- JavaScript: ES2020, strict mode, 1 IIFE per file, no globals, no dependencies, feature-detect before enhancing; storage only in `scheme.js` (section 8).
- Generators: Python standard library only; generated files committed where the site already commits them; every generator gains a `--check` mode; a generator refuses to write a page that contains an en or em dash, an inline style or script, an `on*` attribute, or "what this is" framing.
- Writing: the Clean Language skill applied to every page; Oxford English with -ize; no en or em dashes; numerals for quantities; "ensure that"; never claim that a site, prompt, or audit makes a project compliant, secure, or complete.

### Implementation choices (proceeding as stated unless the owner objects)

- A palette override in `site-palette.css` is written in both forms of its scheme, mirroring `palettes.css` (section 4, item 4), so a change to 1 dark value is the same value on 2 lines of 1 file, and the palette gate fails if the 2 differ. grclibrary.ai's standard asked for 1 value on 1 line. A form with 1 line per value is possible (each value declared once as a site variable and the 4 selector forms pointing at it), at the cost of a second layer of names in the site file and in the gate; the package ships the mirrored form, which the owner's brief named.
- The footer grey (`#4a4a4a` light, `#5c5c5c` dark) becomes a neutral token in `palettes.css`, so `baseline.css` keeps to the tokens-only rule.
- The footer's first and last cards start and end on their own hue, as built, so the bar's ends and the grey tail take a clean colour.
